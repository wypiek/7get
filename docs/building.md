# Building SevenGet

Outputs (both toolchains):

```
build/x86/sevenget.exe            build/x64/sevenget.exe
build/x86/sevenget-repotool.exe   build/x64/sevenget-repotool.exe
build/x86/sevenget_tests.exe      build/x64/sevenget_tests.exe
```

All executables are fully static (no MSVC redistributable, no MinGW DLLs),
console subsystem 6.01, ASLR/DEP enabled, and contain an application manifest
(`asInvoker`, supportedOS Windows 7–11).

## Option A: Windows 10/11 host with Visual Studio 2022

Requirements: Visual Studio 2022 with "Desktop development with C++"
(MSVC v143 and a Windows 10/11 SDK), CMake ≥ 3.21 (bundled with VS), Python 3
(only for the import check).

```
cmake --preset msvc-x64
cmake --build --preset msvc-x64
build\x64\sevenget_tests.exe

cmake --preset msvc-x86
cmake --build --preset msvc-x86
build\x86\sevenget_tests.exe

python tools\check_imports.py build\x64\sevenget.exe build\x86\sevenget.exe
```

Why this toolchain is Windows 7 compatible:
- `_WIN32_WINNT=0x0601` / `NTDDI_VERSION=0x06010000` hide post-Windows 7 APIs
  at compile time.
- The static CRT (`/MT`) of VS 2022 (v143) supports Windows 7 SP1 as a target;
  the linker is given `/SUBSYSTEM:CONSOLE,6.01`.
- `tools/check_imports.py` verifies the import table afterwards.

Microsoft's newest toolsets may eventually drop Windows 7 support from the
static CRT; stay on v143 (VS 2022) for Windows 7 targets and keep running the
import check and the Windows 7 test plan.

> Status: the MSVC x86 and x64 builds are built and tested by the GitHub
> Actions workflow (VS 2022 / MSVC 19.44, Windows Server 2022 runner: build,
> full test suite, import check, `doctor` – all passing on 2026-10-28).
> Day-to-day development used the MinGW-w64 toolchain below.

## Option B: Linux host (or WSL) with MinGW-w64 — used for development

Ubuntu 24.04:

```
sudo apt-get install cmake ninja-build g++-mingw-w64-x86-64-win32 g++-mingw-w64-i686-win32
cmake --preset mingw-x64 && cmake --build --preset mingw-x64
cmake --preset mingw-x86 && cmake --build --preset mingw-x86
python3 tools/check_imports.py build/x64/sevenget.exe build/x86/sevenget.exe
```

Use the `-win32` thread-model compilers: they link against `msvcrt.dll`
(present on every Windows 7) and do not need `libwinpthread`. The GCC 13
win32 thread model uses SRW locks / condition variables (Vista+).

Running the tests on Linux needs Wine (64-bit) and a UTF-8 locale (the tests
use non-ASCII paths):

```
sudo apt-get install wine64
WINEDEBUG=-all LANG=C.UTF-8 wine build/x64/sevenget_tests.exe
```

Wine reports Windows 10 by default; `wine winecfg -v win7` makes it report
Windows 7 (NT 6.1.7601 SP1), which exercises SevenGet's Windows 7 selection
logic. Wine is not Windows 7 – see [windows7-testing.md](windows7-testing.md).

## Tests

`sevenget_tests.exe [filter]` runs all tests (or those whose name contains
`filter`). It creates an isolated `SEVENGET_HOME` under `%TEMP%` with spaces
and non-ASCII characters in the path and removes it afterwards. It needs no
network: the end-to-end test uses a local signed repository and pre-seeds the
download cache (the file is still SHA-256 verified).

| Test file | Covers |
|-----------|--------|
| `test_json.cpp` | strict parser, malformed input, UTF-8, surrogates, depth limit, round trip |
| `test_version.cpp` | version ordering, version/Windows-version validation, time/size formatting |
| `test_manifest.cpp` | schema validation, malicious ids/paths/args/URLs, unknown fields, MSI property rules |
| `test_resolver.cpp` | newest-compatible selection, Windows 7 vs 10, arch rules, scope/type preference, dependencies, cycles |
| `test_security.cpp` | SHA-256 KATs, file tampering, ECDSA (OpenSSL vector), signed index: tampering, key change, forged fingerprint, rollback, equivocation, expiry, name/schema checks |
| `test_process.cpp` | argument quoting vs `CommandLineToArgvW`, uninstall-string splitting, msiexec quoting, real child process with tricky args, exit-code classification |
| `test_database.cpp` | records, constraints, rollback, crash recovery of interrupted transactions, corruption detection, snapshot repair |
| `test_zip.cpp` | entry-name sanitizer, Unicode extraction, zip-slip/ADS/device/symlink/duplicate/truncated archives |
| `test_cli.cpp` | argument parser, usage errors, config, and an end-to-end flow: repo enrollment (wrong/right fingerprint), search/info, dry run, tampered cached file, install, upgrade (user files preserved), rollback and key-substitution attacks, busy lock, locked files, uninstall, history, clean |

ZIP fixtures are generated by `tools/gen_test_zips.py` and committed.

## Release packaging

```
cmake --install build/x64 --prefix out/sevenget-1.0.0-x64      (MinGW / single-config)
cmake --install build/x64 --config Release --prefix out/sevenget-1.0.0-x64   (MSVC)
```

This copies `sevenget.exe`, `sevenget-repotool.exe`, `README.md`, `LICENSE`
and `THIRD_PARTY_NOTICES.md`. Zip the folder per architecture. Before
publishing a release:

1. `python3 tools/check_imports.py out/*/sevenget.exe` passes.
2. `sevenget_tests.exe` passes on x86 and x64.
3. Run the Windows 7 SP1 checklist in [windows7-testing.md](windows7-testing.md).
4. Publish SHA-256 checksums of the release zips. Authenticode-sign the
   executables if you have a code-signing certificate (use a SHA-256
   certificate; Windows 7 needs KB4474419 to validate it).

The GitHub Actions workflow (`.github/workflows/build.yml`) builds all four
combinations, runs the tests (MSVC natively; MinGW x64 under Wine), runs the
import check and uploads the packaged folders as artifacts. It pins
`windows-2022` to keep the VS 2022 toolset; adjust if GitHub retires that image.
